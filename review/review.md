## 2. Предмет и критерии проверки

В соответствии с методическими указаниями к Контрольной точке № 3 (КТ3) выполнена комплексная экспертная оценка объектно-ориентированной программной реализации на платформе Java по следующим критериям:

1. **Соответствие архитектурной модели (UML)**:
   * Наличие в исходном коде всех доменных классов, отраженных на диаграмме `models/classes.drawio` (`classes.png`).
   * Корректность переноса сущностей реляционной схемы 3НФ в объектные классы (`StudioRig`, `Camera`, `CameraModel`, `FrameCapture`, `ScanSession`, `CalibrationProfile`, `CameraOverlapPair`).
   * Соответствие отношений между классами: реализация интерфейсов (`Realization`), наследование (`Generalization`), ассоциации и композиция.
2. **Соблюдение парадигмы объектно-ориентированного программирования (ООП)**:
   * **Инкапсуляция**: закрытие полей спецификатором `private`, обеспечение доступа через методы-геттеры и сеттеры, защита внутренних коллекций от некорректных внешних мутаций.
   * **Наследование и полиморфизм**: наличие иерархии классов с осмысленным переопределением функционала (`AbstractSpatialValidator` $\to$ `BfsSpatialOverlapValidator`).
   * **Интерфейсные контракты**: выделение интерфейса с несколькими взаимозаменяемыми реализациями (`QualityRule` $\to$ `SharpnessQualityRule`, `LuminanceQualityRule`).
3. **Использование стандартных структур данных и коллекций**:
   * Применение стандартной библиотеки коллекций Java (`java.util.List`, `java.util.Map`, `java.util.Set`, `java.util.Queue`, `java.util.ArrayDeque`) вместо низкоуровневых массивов фиксированной длины.
   * Оптимальность выбранных структур данных с точки зрения асимптотической сложности ключевых операций.
4. **Качество, чистота и надежность кода**:
   * Читаемость, самодокументируемость и соблюдение соглашений об оформлении кода (Java Code Conventions).
   * Логическое разделение на пакеты (`model`, `qc`, `topology`, `service`).
   * Обработка граничных ситуаций, деления на ноль, пустых наборов данных и защита от `NullPointerException`.
5. **Сборка, воспроизводимость и тестирование**:
   * Точность и полнота инструкций по сборке и запуску в файле `src/java/README.md`.
   * Воспроизводимость компиляции средствами стандартного JDK компилятором `javac` и успешный запуск в среде виртуальной машины `java`.
   * Совпадение расчетных показателей валидации качества и связности рига с процедурной версией (КТ2).

## 3. Замечания рецензента (Петров Д.К. $\to$ Рассыльщиков И.О.)

По результатам детального статического и динамического анализа исходного кода проекта `Photogrammetry-Studio` сформулированы следующие технические замечания и рекомендации по улучшению:

### Замечание № 1: Несоответствие физической структуры каталогов объявленной иерархии пакетов и проблемы с кодировкой UTF-8 на Windows

* **Файл и место в коде**: `src/java/ru/Main.java` (строка 1), а также общее размещение файлов в каталоге `src/java/ru/`.
* **Описание проблемы**:
  1. В исходных файлах объявлена иерархия пакетов, начинающаяся с `package ru.mirea.photogrammetry;` (а также `ru.mirea.photogrammetry.model`, `ru.mirea.photogrammetry.qc` и т.д.). Однако физически в каталоге `src/java/` отсутствуют промежуточные поддиректории `mirea/photogrammetry/` — файлы размещены непосредственно в `src/java/ru/Main.java`, `src/java/ru/model/` и т.д.
  2. При попытке стандартной компиляции `javac` без явного флага каталога вывода `-d out` сгенерированные файлы классов помещаются в каталог `ru/`, из-за чего последующая команда запуска `java ru.mirea.photogrammetry.Main` аварийно завершается ошибкой загрузчика классов:
     `Error: Could not find or load main class ru.mirea.photogrammetry.Main (ClassNotFoundException)`.
  3. Кроме того, на платформе Windows без явного указания кодировки компилятор `javac` по умолчанию использует локаль `windows-1251`, что приводит к 25 критическим ошибкам `unmappable character (0x98) for encoding windows-1251` из-за символов кириллицы в консольных строках и Javadoc-комментариях.
* **Предложение по исправлению**:
  1. Привести физическую структуру папок в точное соответствие пакетному имени Java:
     `src/java/ru/mirea/photogrammetry/{Main.java, model/, qc/, topology/, service/}`.
  2. В инструкции `src/java/README.md` зафиксировать параметры компиляции и запуска с обязательным указанием кодировки UTF-8 и целевого каталога сборки `out`:
     ```powershell
     javac -encoding UTF-8 -d out (Get-ChildItem -Path ru -Recurse -Filter *.java).FullName
     java -Dfile.encoding=UTF-8 -cp out ru.mirea.photogrammetry.Main
     ```

### Замечание № 2: Неоптимальная асимптотическая сложность при построении графа смежности камер

* **Файл и место в коде**: `src/java/ru/topology/AbstractSpatialValidator.java`, строки 29–35 (метод `buildAdjacencyGraph`).
* **Описание проблемы**:
  В методе построения графа смежности списки инцидентных вершин объявлены как `List<Integer>` (`ArrayList<Integer>`):
  ```java
  List<Integer> n1 = graph.get(c1);
  if (!n1.contains(c2)) n1.add(c2);
  List<Integer> n2 = graph.get(c2);
  if (!n2.contains(c1)) n2.add(c1);
  ```
  Проверка `!n1.contains(c2)` на типе `ArrayList` выполняет линейный перебор элементов за $O(\deg(v))$. При обработке плотного фотограмметрического рига с большим числом стереопар ($P$) суммарная сложность заполнения графа возрастает до $O(P \cdot \bar{k})$.
* **Предложение по исправлению**:
  Организовать внутреннее представление графа на базе интерфейса `Set` с сохранением порядка вставки: `Map<Integer, Set<Integer>> graph = new LinkedHashMap<>()`. Использование `LinkedHashSet<Integer>` обеспечивает автоматическую фильтрацию дубликатов ребер методом `n1.add(c2)` с константной временной сложностью $O(1)$, что гарантирует строгую оценку времени построения графа $O(K + P)$. При необходимости отдачи наружу `Map<Integer, List<Integer>>` преобразование наборов в списки выполняется однократно на выходе из метода.

### Замечание № 3: Граничные условия алгоритма BFS и обработка несвязных компонент топологии

* **Файл и место в коде**: `src/java/ru/topology/BfsSpatialOverlapValidator.java`, строки 23–45 (метод `validateTopology`).
* **Описание проблемы**:
  1. При передаче пустого списка камер `cameras.isEmpty()` блок BFS пропускается, однако проверка связности `visited.size() == cameras.size()` вычисляет `0 == 0 -> true`, а список изолированных камер пуст. Метод возвращает `isTopologyValid = true` для пустой студии без камер, что некорректно по смыслу предметной области.
  2. Если граф камер распадается на две изолированные группы (например, полусфера А и полусфера Б без взаимного перекрытия $\ge 60\%$), запуск BFS из вершины `cameras.get(0)` обойдет только первую компоненту. Метод зафиксирует `visited.size() != cameras.size()`, но не локализует состав недостижимых камер и не определит количество изолированных подграфов.
* **Предложение по исправлению**:
  1. Добавить явную проверку граничного условия в начале метода:
     ```java
     if (cameras == null || cameras.isEmpty()) {
         return new TopologyValidationResult(minOverlapPercentage, Collections.emptyMap(), 
                 Collections.emptyList(), false, false, 0, 0);
     }
     ```
  2. Дополнить валидатор подсчетом компонент связности: если после завершения первого BFS остались непосещенные вершины, запускать обход для следующей непосещенной камеры с формированием списка несвязных кластеров камер для информативного диагностического отчета.

### Замечание № 4: Небезопасная ручная сборка JSON-манифеста и зависимость от локали ОС

* **Файл и место в коде**: `src/java/ru/service/ManifestExportService.java`, строки 21–36 (метод `generateManifestJson`).
* **Описание проблемы**:
  1. Метаданные сессии (`target_object`, `operator`, `lighting_preset`) конкатенируются в строку JSON напрямую через форматирование без экранирования служебных символов. Если наименование объекта оцифровки или пресета освещения будет содержать кавычки (например, `Ассет "Рыцарь"`), сгенерированный JSON-документ окажется синтаксически поврежден и не сможет быть прочитан внешним SfM-конвейером (Meshroom, RealityCapture).
  2. В строках 21–32 используется `String.format(...)` без передачи первого аргумента `Locale.US`, тогда как в строке 33 для вывода процентов покрытия `Locale.US` передан явно. Отсутствие единого подхода к локализации создает риск расхождения формата чисел на различных платформах.
* **Предложение по исправлению**:
  1. Добавить вспомогательный метод экранирования строковых значений перед их помещением в JSON:
     ```java
     private static String escapeJson(String value) {
         if (value == null) return "";
         return value.replace("\\", "\\\\")
                     .replace("\"", "\\\"")
                     .replace("\b", "\\b")
                     .replace("\f", "\\f")
                     .replace("\n", "\\n")
                     .replace("\r", "\\r")
                     .replace("\t", "\\t");
     }
     ```
  2. Использовать `String.format(Locale.US, ...)` унифицированно во всех строках формирования манифеста.

* **Предложение по улучшению**:
  Добавить на диаграмму классов сервисный слой (`ManifestExportService`, `DataRepository`) и типы отчетов, отобразив отношения зависимости (`Dependency`, пунктирные направленные стрелки) от сервисов к доменным сущностям и валидаторам.
